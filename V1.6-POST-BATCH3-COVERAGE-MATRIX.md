# V1.6 Post-Batch 3 — Reading / Listening Coverage Matrix

Date: 2026-08-27

## Purpose

V1.6 Batch 3 is production-closed. Before adding another Reading / Listening Repair unit or another Core → Lab route, the project now audits **all recurring Reading / Listening error families** rather than selecting a small candidate list by hand.

The goal is to distinguish five different states:

1. **V/G-REPAIR** — the recurring Reading/Listening signal is already owned by the cross-skill V1.4 Vocabulary / Grammar Repair layer (`VG04` / `VG05`);
2. **SKILL-REPAIR** — the recurring family already has an evidence-driven RR/LR Repair owner;
3. **ROUTED-REUSE** — the family is already sent back to existing Core / Question Type Lab practice;
4. **TAUGHT-UNROUTED** — existing instructional content directly owns the error tag, but Error Notebook / Improve does not yet have an explicit reuse route for that family;
5. **GAP-REVIEW** — no V/G Repair owner, no RR/LR Skill Repair owner, no existing-practice route, and no exact instructional error-tag owner was found.

## Scope

`tests/audit-skill-coverage-matrix-v16.mjs` scans the same registered content layers used by the canonical error-tag audit:

- base Core data;
- curriculum extensions;
- Question Type Labs;
- Mini Tests;
- Full Mock.

The audit includes `data.js` itself so the coverage matrix and the canonical 388-question error-tag inventory use the same source boundary.

Only Reading / Listening semantic families with at least **3 tagged questions** enter the recurring matrix.

The matrix is generated from the real registered question bank and is part of `npm test`, so later content changes automatically change the audit output.

## Classification precedence

For each recurring `skill:family` row:

`V/G REPAIR → RR/LR SKILL REPAIR → EXISTING-PRACTICE ROUTE → EXACT CORE/LAB TAG OWNER → GAP REVIEW`

This precedence is intentional.

A Reading / Listening family may already be deliberately treated by the cross-skill language-system Repair layer. For example, paraphrase errors are owned by `VG04`, and answer-type prediction errors are owned by `VG05`; these must not be mistaken for missing RR/LR routing.

A family may also still have older Core/Lab teaching after an RR/LR Repair exists. Once the project has deliberately created an evidence-driven Skill Repair owner, the matrix records the active learner treatment as **SKILL-REPAIR** rather than treating that overlap as a new routing request.

Likewise, an explicit Batch 3 route is considered stronger evidence of current product handling than simply finding a matching error tag in an instructional lesson.

## Decision policy after the audit

The matrix is a decision gate, not an automatic content generator.

### `V/G-REPAIR`

Do not create a duplicate RR/LR unit simply because the originating question is Reading or Listening. Re-open the decision only if deployed evidence shows that the language-system Repair does not transfer back to the skill task.

### `SKILL-REPAIR`

Do not create another lesson from frequency alone. Re-check mastery and deployed evidence only if learner behavior shows the existing Repair is insufficient.

### `ROUTED-REUSE`

Do not duplicate teaching. Refine the Core → Lab route only if deployed evidence shows the current mapping is too broad or repeatedly sends learners to the wrong transfer task.

### `TAUGHT-UNROUTED`

This is primarily a **routing candidate**, not a Repair candidate. Review whether the existing lesson truly teaches the decision well enough and whether an Error Notebook CTA would reduce friction.

### `GAP-REVIEW`

Inspect the actual questions before deciding anything. A gap can mean:

- a real untreated reasoning/process skill;
- a narrow question-type behavior that should route to an existing Lab;
- inconsistent tagging;
- a family too heterogeneous to deserve one lesson.

Only the first case should normally lead to a new RR/LR Repair unit.
