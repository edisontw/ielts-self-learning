# V1.6 Batch 3 — Existing-Practice Routing

Date: 2026-08-27

## Goal

V1.6 Batch 2 established that several high-frequency Reading / Listening error families do **not** need another Repair lesson because existing Core / Question Type Lab content already teaches the required decision.

Batch 3 closes the next gap: when one of those errors reaches Error Notebook / Improve, the learner should be sent back to the right existing teaching instead of seeing only a generic error record or an unnecessary new Repair unit.

## Routing principle

Priority order:

1. **Retry the original lesson question** when the saved lesson item is directly retriable;
2. otherwise **return to existing Core teaching**, then use a Question Type Lab for transfer;
3. use dedicated **Skill Repair** only for families that the overlap audit identified as real instructional gaps (currently RR01, RR02, LR01).

This keeps three different learner actions visually and behaviorally separate:

- Retry original question;
- Review existing practice;
- Open evidence-driven Repair.

## Data-driven route map

`existing-practice-routing-v16.js` owns the recommendation map.

| Error family | Active evidence | Primary Core review | Transfer Lab |
| --- | ---: | --- | --- |
| Reading detail | 21 | R02 | QR03 |
| Reading heading-specific detail | included above | R05 | QR02 |
| Listening detail | 16 | L05 | QL05 |
| Listening distractor | 14 | L04 | QL01 |
| Listening correction | 11 | L04 | QL06 |
| Reading scope | 10 | R04 | QR01 |

Specific tags are evaluated before generic Full Mock fallbacks. For example:

- `reading-heading-detail` / `reading-detail-confusion` → R05 → QR02;
- `reading-mcq-detail` → R02 → QR03;
- generic Full Mock `detail` + `skill=reading` → R02 → QR03;
- generic Full Mock `detail` + `skill=listening` → L05 → QL05.

The same compact Full Mock tag therefore cannot cross-route between skills.

## Skill Repair ownership stays separate

Existing-practice routing deliberately does **not** claim:

- Reading `main-idea` → RR01;
- Reading `inference` → RR02;
- Listening `number` → LR01.

This prevents the new reuse surface from competing with the evidence-driven Skill Repair units introduced in V1.6 Batch 1 / 2.

## Improve UX

`existing-practice-routing-runtime-v16.js` adds a separate Improve section:

**Return to existing practice — These errors are already taught**

Only active, non-fixed, non-retriable transfer errors are counted.

Each family card gives one simple sequence:

`REVIEW CORE → PRACTISE LAB`

The card also shows the audited evidence count and the wider Core/Lab coverage used to justify reuse rather than another Repair lesson.

The surface is inserted after the RR/LR Skill Repair section so the distinction remains visible:

1. Vocabulary / Grammar Repair;
2. Reading / Listening Skill Repair;
3. Return to existing Core / Lab practice.

## Error Notebook UX

For an active error that cannot directly retry its source item, Error Notebook adds:

- `Review <Core ID>`
- `Practise <Lab ID>`

For a normal lesson error that already has `Retry question`, Batch 3 adds **no competing route CTA**. The original retry remains the stronger action.

No error is automatically marked corrected by opening a Core or Lab route. Existing correction / retry evidence rules remain unchanged.

## Mini Test retry boundary

Production review exposed a boundary issue after Batch 3 first merged: Mini Test definitions are registered into the shared `LESSONS` array, so a generic “lesson contains this question” check could incorrectly make a Mini Test item appear eligible for single-question Retry after registration.

PR #37 hardened `repair-retry-v1.js` so direct lesson Retry explicitly rejects Mini Test / Test Mode lessons. The regression now loads the real MR01–MR04 / ML01–ML04 production registry before asserting that a Mini Test item cannot be unlocked as a single question.

The resulting contract is:

- standard Practice Mode lesson error → direct question Retry;
- Mini Test error → review / existing-practice routing / full Test Mode retake;
- Mini Test saved answers are not cleared by the existing-practice routing path.

## Architecture

Batch 3 is recommendation-only.

It adds:

- `existing-practice-routing-v16.js` — data-only routing rules;
- `existing-practice-routing-runtime-v16.js` — read-only Improve / Error Notebook rendering.

It does not add:

- a lesson;
- a localStorage key;
- a backup field;
- a completion state;
- a polling loop;
- a MutationObserver;
- a new denominator.

The runtime uses the shared V1.5 `registerRenderEnhancement` lifecycle and existing delegated `data-lesson` navigation.

## Next direction

Do not add another RR/LR lesson from error frequency alone.

Re-run the coverage-overlap audit before any later extension. The next routing refinement should be evidence-led: only make the current Core → Lab recommendation more specific if deployed learner evidence shows that the present mapping is too broad or repeatedly sends learners to the wrong practice target.
