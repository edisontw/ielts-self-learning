# V1.5 DOM Consolidation

Date: 2026-08-27

## Goal

Reduce progressive DOM-patching technical debt without changing learner-visible behaviour, URL contracts, localStorage schemas, backup/import semantics, or Repair mastery evidence.

This work is intentionally staged. V1.5 does not combine every mature runtime into `app.js` in one change because the deployed learner journey is already stable and heavily regression-tested.

## Batch 1 — deterministic Repair render lifecycle

Production previously had two supplemental continuous scanners:

1. `repair-extension-v14.js` created a full-document `MutationObserver` to keep VG04/VG05 rendered after the base app replaced `#main`.
2. `learn-repair-cards.js` called `setInterval(apply, 1000)` to rediscover the Learn page and inject Repair cards.

Batch 1 replaces both with:

- `repair-registry-v15.js` — data-only registration of VG04/VG05 and their Error Notebook tag families;
- `render-lifecycle-v15.js` — one shared, microtask-coalesced event lifecycle driven by startup completion, route changes, app clicks, and adaptive-state changes;
- `repair-route-v15.js` — Repair route renderer using the existing `data-lrv` interaction contract and `repairReadyToComplete` mastery gate;
- `learn-repair-index-v15.js` — Learn Repair cards rendered only when an actual render-relevant event occurs.

`render-lifecycle-v15.js` imports `app.js` as a startup barrier. Because `app.js` uses top-level `await` while loading Placement data, enhancement registration now begins only after the base app's first render has completed. This avoids relying on MutationObserver polling or DOM timing guesses.

Repair note input deliberately does not schedule a render pass. The interaction runtime persists the note while the active textarea remains mounted, preserving focus and caret position during typing.

Legacy filenames remain compatibility shims but are not loaded by production `index.html`.

Batch 1 merged in PR #28 and passed both the pull-request validation gate and post-merge main validation before GitHub Pages deployment.

## Batch 2 — adaptive/runtime consolidation

Batch 2 was merged in PR #30 from a clean branch based directly on the post-#28 `main`. The earlier stacked PR #29 was closed without merge so the review diff contained only Batch 2 changes.

The remaining continuous discovery layers are removed:

1. `adaptive.js` no longer creates a document-wide `MutationObserver`; `injectAdaptiveUI` is registered with the shared lifecycle.
2. `learning-runtime-v3.js` no longer runs `setInterval(..., 1000)` or its private hashchange refresh loop; `apply` is registered with the shared lifecycle.
3. `repair-route-v15.js` now resolves registered Repair lessons from `REPAIR_LESSONS`, so VG01–VG05 use one data-driven route renderer instead of separate VG01–VG03 and VG04–VG05 render paths.
4. `learning-runtime-v3.js` imports `repairReadyToComplete` and `resetRepairAnswer` explicitly rather than relying on runtime globals.
5. adaptive silent persistence compares serialized state before writing, avoiding redundant localStorage writes on lifecycle passes.
6. the legacy retry-loop regression now follows the unified Repair renderer rather than asserting that Repair UI still belongs to `learning-runtime-v3.js`.

The callback order is intentional: adaptive UI registers before learning-runtime enhancements, so Improve receives Review/Repair anchors before Vocabulary Review tries to attach, and Today receives its adaptive root before observed-performance rendering refines it.

## Contracts preserved

- Standard Repair URLs remain `#/lesson/VG01` through `#/lesson/VG05`.
- Error-driven routing remains based on the V1.4 audited tag families.
- Guided practice still follows `wrong → Retry → correct all → Finish`.
- `ielts-adaptive-v1` remains unchanged.
- Core learner data and backup schema remain unchanged.
- The first 30-unit curriculum denominator remains unchanged; VG04/VG05 remain Repair extensions.
- Learn still shows all registered Repair lessons.
- Vocabulary Review and observed skill performance keep their existing storage structures and interaction contracts.

## Regression guardrails

Validation rejects:

- `MutationObserver` in the adaptive / Repair render lifecycle;
- `setInterval` in the learning / Repair lifecycle;
- a second hard-coded `VG0[1-3]` Repair renderer in `learning-runtime-v3.js`;
- a global input-triggered enhancement pass that would replace an active Repair note textarea;
- a stale Repair fingerprint short-circuit unless the expected rendered route DOM is still present.

Browser smoke preflights the V1.5 modules and directly checks:

- Learn Repair index content;
- VG01 and VG03 from the original core Repair set;
- VG04 and VG05 from the error-driven Repair extension;
- existing core, Lab, Writing, Speaking, Mini Test and mobile IELTS routes.

Each batch was mergeable only after a fresh validation run passed both:

1. the complete `npm test` suite;
2. the complete browser smoke suite.

PR #30 Run #254 passed the complete unit/regression suite and browser smoke, including Learn Repair plus direct VG01, VG03, VG04 and VG05 routes. The final PR head also passed a fresh complete validation run before merge.

A GitHub Actions scheduling/check-suite anomaly on the original PR #27 produced a workflow-level failure while its only job remained queued with no runner and no steps. PR #28 superseded that PR; no code bypass was accepted in place of the test gate.

## Next implementation direction

With the render lifecycle stable in production, the next learning-value cycle should be evidence-driven content expansion rather than another runtime layer. The existing error-tag audit shows large recurring Reading / Listening process families that are not Vocabulary / Grammar problems, especially detail, number, main idea, distractor, scope, correction and inference.

The next cycle should preserve the 30-unit core denominator and add targeted repair / transfer content only where repeated learner evidence supports it. Account sync / PWA remains optional infrastructure and is deferred unless a concrete product need outweighs the local-first model.
