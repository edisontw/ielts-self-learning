**Status:** STARTED  
**Created:** 2026-08-30

---

## 1. Why V1.8 exists

The site has moved past the prototype/content-scarcity phase. The major curriculum, Lab, Mini Test, Full Mock, Repair, Study Plan, productive-skill and local-data systems already exist.

The current optimization question is not:

> What else can we add?

It is:

> Can a learner move through the existing system without having to understand the site's architecture or decide what to do next?

V1.8 therefore targets **learner-flow quality, continuity and friction reduction**.

---

## 2. North-star learner behavior

The preferred recurring loop is:

`OPEN TODAY → DO ONE HIGH-VALUE ACTION → GET FEEDBACK → FIX/RETRY → RETURN → CONTINUE PLAN`

At every major state transition, the UI should answer:

1. What happened?
2. What matters most?
3. What should I do next?
4. How do I return to what I was doing?

The site should avoid making the learner choose among many equally prominent next actions.

## 4. Milestone 1 — Journey audit before redesign

Audit the current deployed behavior first. Do not redesign from screenshots alone.

### Journey A — New learner

Target path:

`Today/Landing → Set goal → Quick Placement → Result → Study Plan or Start → Recommended lesson → Today`

Audit:

- [ ] Is the first primary action obvious within a few seconds?
- [ ] Does Quick Placement completion lead to one clear next step?
- [ ] Can Study Plan be deferred without creating a dead end?
- [ ] Is the difference between Today / Learn / IELTS / Improve understandable without reading long help text?
- [ ] Is the learner pushed toward Today rather than random browsing?
- [ ] Mobile 360/390/430 flow remains usable.

### Journey B — Returning learner

Target path:

`Open site → Today → due review OR plan next session → start immediately`

Audit:

- [ ] Exactly one visually dominant primary action.
- [ ] Due review takes priority when pedagogically appropriate.
- [ ] Completed lessons are not resurfaced as new work.
- [ ] Locked/prerequisite-inappropriate content is not recommended.
- [ ] Secondary shortcuts do not compete with the primary recommendation.

### Journey C — Objective error / repair / retry

Target path:

`Wrong → explanation → direct Retry OR owner/Repair → mastery → Return → continue original context`

Audit:

- [ ] Direct lesson Retry remains first priority when valid.
- [ ] Existing owner reuse remains preferred to new Repair.
- [ ] Error Notebook CTA label explains why the destination is recommended.
- [ ] After mastery, there is an explicit Return/Continue action.
- [ ] The original source context (lesson/Lab/Mini Test/Mock) is preserved where useful.
- [ ] No Test Mode error becomes a fake single-question retry.

### Journey D — Mini Test / Full Mock review

Target path:

`Submit → result summary → 2–3 priority families → one next action → targeted practice → return to review/plan`

Audit:

- [ ] Result pages do not lead with an overwhelming flat list of wrong items.
- [ ] Priority grouping is skill-aware and evidence-based.
- [ ] One recommended next action is surfaced before the full detail list.
- [ ] Errors still remain individually inspectable/saveable.
- [ ] The learner can return from targeted practice to the relevant test review context.
- [ ] MA01/MA02 identities remain distinct in history and Error Notebook.

### Journey E — Writing / Speaking productive loop

Target path:

`Attempt → self-check → AI prompt → external feedback → return → save 2–3 priorities → rewrite/retry → compare`

Audit:

- [ ] The AI prompt is not presented as completion.
- [ ] Return-to-site instructions are obvious.
- [ ] Saving AI feedback remains limited to actionable coaching priorities, not imported scoring.
- [ ] Revision/retry is the dominant next step after feedback is saved.
- [ ] Before/after comparison emphasizes process improvement, not pseudo-precision.
- [ ] Draft/transcript state survives normal navigation and backup/restore.

### Milestone 1 output

Produce a short evidence table:

| Journey | Friction | Severity | Evidence | Smallest useful change | Regression test |
|---|---|---:|---|---|---|

Do not implement speculative visual redesigns that are not tied to an observed friction point.

## 5. Milestone 2 — Navigation and context continuity

Likely high-value capability: preserve the learner's **origin context** when routing to review/repair.

Examples:

- Lesson question → Error Notebook/Repair → `Return to R04`
- QL03 Set B → targeted Repair → `Continue QL03 Set B review`
- MR04 result → R02/QR06 practice → `Return to MR04 review`
- MA02 Reading result → RR02 → `Return to MA02 Reading review`

Design constraints:

- Do not create brittle browser-history assumptions.
- Prefer explicit lightweight origin metadata / return intent when needed.
- Do not break old local learner data.
- Return destination must be safe if the original context no longer exists.
- Test Mode state must not accidentally reopen an active submitted attempt as editable.

Acceptance:

- [ ] Major repair/review CTAs preserve a meaningful return destination.
- [ ] `Return` labels name the destination when possible.
- [ ] Returning does not lose saved progress/errors.
- [ ] Reload and mobile navigation remain safe.

## 6. Milestone 3 — Result prioritization

### Problem to solve

Large tests can produce many wrong items, but the learner needs **a small number of actionable priorities**, not only a list.

### Desired result hierarchy

1. Overall attempt summary.
2. `Your priorities` — ideally 2–3 coherent skill/error families.
3. `Recommended next step` — one action.
4. Full item-by-item review below.

### Guardrails

- Group by semantic family **within skill**.
- Do not aggregate sparse unrelated tags just to make a recommendation.
- Existing V1.6/V1.7 teaching-owner/route rules remain authoritative.
- Do not create a new Repair from the result page.
- If evidence is insufficient, recommend item review / existing taught context instead of inventing a priority.
- Do not calculate an official or false precise IELTS band.

Acceptance:

- [ ] Mini Test and Full Mock results surface priorities before the flat error list.
- [ ] Priority links use existing exact owners/routes.
- [ ] Sparse evidence remains visible but does not become a false intervention.
- [ ] MA01/MA02 histories remain schema-compatible.

## 7. Milestone 4 — Today simplification

Today should answer one question:

> What should I do now?

Desired hierarchy:

1. **Primary:** due review / current plan / highest-value recommended activity.
2. **Secondary:** continue unfinished work or one compact alternative.
3. **Tertiary:** browse Learn / IELTS / Improve.

Audit and optimize:

- [ ] Reduce competing card prominence.
- [ ] Explain the recommendation in one short sentence when useful.
- [ ] Avoid repeating the same lesson too frequently.
- [ ] Preserve Learn-by-Time behavior.
- [ ] Keep completed/locked content out of inappropriate recommendations.
- [ ] Returning learner can launch the primary task with one click/tap.

---

## 8. Milestone 5 — Productive skill continuation

Improve the visible loop after external AI feedback.

Desired state:

`Feedback received → Save priorities → Revise/Retry now`

Potential UI improvements should be judged by whether they:

- reduce the chance that the learner stops after receiving feedback;
- reconnect each priority to the next revision/retry;
- preserve the distinction between Writing/Speaking process evidence and objective accuracy;
- avoid imported AI scoring.

Acceptance:

- [ ] One dominant rewrite/retry CTA after feedback is stored.
- [ ] Previous attempt remains available for comparison.
- [ ] Speaking transcript-only feedback does not claim pronunciation assessment.
- [ ] Existing portable backup/import behavior remains valid.
